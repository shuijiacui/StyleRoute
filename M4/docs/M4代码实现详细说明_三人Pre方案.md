## 1 职责边界和整条调用链

### 1.1 三位技术成员分别解决什么

| 成员 | 需要回答的问题 | 输入 | 输出 |
|---|---|---|---|
| **你 M4** | 给定图片和强度，如何稳定生成、展示和导出？ | 原图、风格图、区域掩码、区域强度 | 生成图片、缓存、应用、明信片 PNG、性能记录 |
| **M5** | 原图应该分成哪些区域，区域之间是什么关系？ | 你处理后的内容图、目标特征尺寸 | 标签图、区域编号、软掩码、邻接关系与边权 |
| **M6** | 怎样评分、限制风格损失，并搜索区域强度？ | 生成接口、区域信息、评分与搜索配置 | 最佳已发现可行结果、强度数组、搜索日志与评价脚本 |
| **P3** | 如何整理并讲清实验结果？ | 统一实验脚本、配置、原始输出 | 实验运行记录、对比图表及展示材料；算法结果解释仍由对应技术成员核查 |

**注意代号变化：旧两人 pre 文档曾把“区域模块”分给 M4。最终三人 pre 方案以本表为准，你现在负责生成与应用，区域模块属于 M5。**

### 1.2 一次完整运行怎样发生

```text
用户上传内容图和风格图
        │
        ▼
M4 读取图片、统一预处理，准备 AdaIN 特征缓存
        │ 交出处理后的内容图和特征尺寸
        ▼
M5 划分区域、构建关系图、生成软掩码
        │ 交出标签、区域编号和掩码
        ▼
M6 提出一组区域强度，例如 [0.3, 0.6, 0.9, ...]
        │
        ▼
M4 将强度应用到缓存特征上，统一解码整张图片
        │
        ▼
M6 评分、检查约束、决定下一组强度
        │ 多轮循环，内容和风格特征保持复用
        ▼
M6 返回最佳已发现可行结果与搜索记录
        │
        ▼
M4 显示结果、排版文字、生成并下载明信片
```

你的界面是调用这些模块的入口，不应该把 M5 的分割算法或 M6 的搜索算法重新写一份放进 `app.py`。

### 1.3 你的实现范围

必做：固定预处理、权重加载、全局 AdaIN、特征缓存、区域融合、单图命令入口、简单界面、中文 PNG、性能测量和运行说明。

由其他成员提供：SLIC 与合并、区域边权、Q/T/S 评分、约束与接受规则、搜索器、主实验批量调度。你需要接入并测量这些接口，不能用假的搜索结果替代最终集成。

本阶段不增加新网络训练、SAM、云部署、登录系统、自动文案或高分辨率重建。生成器先固定为单图、单风格参考、FP32 推理。

最后一项原文使用了交易算法和金融计算的措辞，与本项目题目不一致。此处保留原名，将“算法正确性、效率、冗余计算”作为本项目拟准备的对应证据；具体评分适用口径以教师解释为准，不为这段模板措辞额外加入金融功能。

### 2.2 Coding style 应具体做到什么

- 模型类只负责模型；`app.py` 负责交互；排版函数不加载神经网络；性能脚本不修改业务算法。
- 用 `content_features`、`style_features`、`feature_alpha_map` 等名称表达含义，避免到处出现 `x1`、`temp2`、`img_final_new`。
- 对外函数写清输入形状、范围、设备、返回值和失败条件。例如 `[1,3,H,W]` 与 `[N,Hf,Wf]` 不能只靠口头约定。
- 注释解释不直观的原因：为什么生成器不做普通 ImageNet 标准化、为什么掩码要归一化、为什么计时前后同步 GPU。
- 使用小函数拆分读取、预处理、准备特征、融合、解码、导出；避免一个几百行函数包办所有事。
- 路径、尺寸、设备、权重文件和字体位置从配置读取。文件路径用 `pathlib.Path`，不把你电脑的用户名写死在代码中。
- `FileNotFoundError`、`ValueError` 等错误应该指出缺什么或哪里不合法；不要用 `except: pass` 隐藏失败。
- 复用代码保留原许可与来源记录；自写包装和兼容性修改单独说明。
- 每个可执行脚本有明确入口；导入模块不能自动启动页面、下载整个数据集或开始批量实验。

这些是本项目为对齐评分而制定的工程要求，不是截图额外列出的逐条官方规则。

### 2.3 Functionality 应如何判定完成

“我在自己的 Notebook 里生成过一张图”不算完整交付。至少需要：

1. 组员根据 README 安装实际验证过的环境，按说明放好权重。
2. 用一个明确命令生成默认 AdaIN 结果。
3. 通过区域接口生成结果，并通过常数强度一致性检查。
4. 在页面上传两图后完成默认生成和真实搜索流程。
5. 加入中文标题和正文，预览并下载 PNG，重新打开文件能看到完整内容。
6. 缺少权重、坏图片、掩码不匹配等情况有明确提示。
7. 保存足够的输入、配置和版本信息，能重现该结果。

Good 档中的“超过 80%”不作为主动删减功能的目标。提交目标应是本方案已约定的全部必做功能可运行。

### 2.4 Performance 应如何准备证据

实现模型只加载一次、同图对只编码一次、不同候选只做必要的融合与解码；关闭梯度；减少搜索循环中的磁盘读写和设备往返。然后用同一硬件、尺寸和精度进行真实测量。

**缓存不意味着新候选不需要计算。** 内容和风格编码可以复用，但新的区域强度通常仍需完整解码；M6 的新结果评分也有额外计算。没有实测前，不承诺帧率、加速倍数或搜索总耗时。

## 4 配置和数据约定

### 4.1 建议的起步配置

以下是可操作的起点，未经本机验证；团队在试运行后统一冻结。JSON 用项目相对路径，运行时以项目根目录解析。

```json
{
  "content_hw": [256, 256],
  "content_resize_mode": "fit_center_crop",
  "style_long_side": 256,
  "minimum_style_short_side": 32,
  "default_alpha": 0.6,
  "allowed_region_alphas": [0.3, 0.6, 0.9],
  "device": "auto",
  "dtype": "float32",
  "adain_eps": 0.00001,
  "encoder_checkpoint": "weights/vgg_normalized.pth",
  "decoder_checkpoint": "weights/decoder.pth",
  "font_path": "assets/fonts/cjk.ttf",
  "run_root": "runs"
}
```

`minimum_style_short_side` 用于拒绝不适合当前网络的极端窄图；不要为了凑尺寸把风格图随意拉伸。如果需要另一种缩放策略，在试运行中明确改配置并对所有方法统一使用。

`vgg_normalized.pth` 是项目内约定名称。上游 README 和测试入口中出现过 `normalized` / `normalised` 拼写差异，应以实际文件和权重清单为准，不能只凭拼写猜测文件存在。[S2][S3]

`device=auto` 表示可用时选择 CUDA，否则选择 CPU；日志必须写实际设备。若显式要求 CUDA 却不可用，应明确报错，不偷偷回落后继续把结果标成 GPU 性能。

### 4.2 核心张量约定

| 对象 | 形状 | 范围/类型 | 谁提供 |
|---|---|---|---|
| 内容图张量 | `[1, 3, H, W]` | RGB、FP32、`[0,1]`，起步 `H=W=256` | M4 |
| 风格图张量 | `[1, 3, Hs, Ws]` | RGB、FP32、`[0,1]`；保持比例缩放 | M4 |
| 内容特征 | `[1, C, Hf, Wf]` | 固定生成器编码器输出 | M4 |
| AdaIN 特征 | 与内容特征相同 | 同图对的完整统计匹配特征 | M4 |
| 硬区域标签 | `[H, W]` | 整数，区域编号连续且从零开始 | M5 |
| 区域软掩码 | `[N, Hf, Wf]` | FP32、非负，每个位置各区域权重和约等于一 | M5；M4校验 |
| 区域强度 | `[N]` | 和掩码顺序严格一致，正式搜索使用三个允许取值 | M6 |
| 强度图 | `[1, 1, Hf, Wf]` | 加权组合后的空间强度 | M4 |
| 规范生成图 | `[1, 3, H, W]` | FP32、裁到`[0,1]`，评分、预览、导出的共同来源 | M4 |

在上述复用架构下，256×256 内容图到 relu4_1 的典型形状为 `[1,512,32,32]`。代码仍应读取真实特征形状，而不是到处硬编码 32。[S4]

## 5 模块一 数据准备

### 5.1 内容图保持 Places365

使用 `torchvision.datasets.Places365` 的 `split="val"`、`small=True`。`small` 是图像尺寸较小的版本，不代表只下载十二张；下载和解压可能涉及整个验证集包。[S5]

固定抽样：

| 类别 | 官方类别编号 | 取图规则 | 用途 |
|---|---:|---|---|
| beach | 48 | 确认类别映射后按相对文件名排序取四张 | 第一张试运行，后三张正式评价 |
| mountain | 232 | 同上 | 同上 |
| downtown | 125 | 同上 | 同上 |

类别编号来自官方类别表，程序仍应从所使用发布版的映射文件核对名称，不能在映射不一致时继续抽错类别。[S6]

你要实现：

1. 显式传入数据根目录；存在数据时直接复用。
2. 下载开关默认关闭，只有用户运行准备命令并传开关才联网获取。
3. 读取发布版的样本列表与标签，根据类别筛选；不要假设验证图像目录按类别建文件夹。
4. 按相对文件名稳定排序，选择并验证可读取的文件。
5. 坏文件、缺类别或数量不足时报告；若采用“顺延下一张”的替代规则，必须预先固定并记录，不凭效果手工挑图。
6. 保存十二张选中图及其发布版相对路径、类别、用途、文件 SHA256。
7. 单独列出九张正式内容图和三张试运行图，禁止重叠。

只需要获取与登记图像，不需要下载或训练 Places365 分类模型。

## 6 模块二 AdaIN 底座

### 6.1 复用路线

方法依据是 Huang 与 Belongie 的 AdaIN。原作者代码使用 Torch；可以复用非官方 PyTorch 移植的网络定义和配套权重，但应如实注明其身份与归档状态。[S1][S2]

具体操作：

1. 固定参考代码的上游提交或发布版，登记 URL 与许可证。
2. 从其发布入口取得编码器与解码器权重，记录实际文件名和 SHA256。[S11]
3. 先运行单图全局风格迁移，确认环境与权重可用，再增加区域融合。
4. 保留网络定义的来源；兼容性修改记录在 `THIRD_PARTY.md`。

这份说明没有验证你的电脑能否访问或运行该发布版。第一阶段必须真实下载、加载并保存一张结果，不能把 README 中的链接存在等同于本地跑通。

### 6.2 图片读取与预处理

`models/preprocessing.py` 至少提供 `load_rgb`、`prepare_content`、`prepare_style` 和图像指纹函数。

处理规则：

1. 支持本地路径和上传字节；主动解码，检查文件是否真的是可读取图片。
2. 根据 EXIF 修正方向；透明图在明确的白色背景上合成，再转 RGB；灰度图转三通道。
3. 内容图保持比例缩放后中心裁成 256×256，保存变换规则与原始尺寸，不直接把任意照片拉伸成正方形。
4. 风格图长边缩放到配置尺寸、保持比例；不做随机裁剪或随机增强。
5. 内容图处理完成后，把同一张处理结果交给 M5；不能让区域标签来自原图、特征来自另一张裁剪图。
6. 转成 FP32 的 RGB `[0,1]` 张量，增加 batch 维，并移到明确设备。

**关键：复用此 AdaIN 生成器时，遵循其配套权重的输入约定，不额外套用普通 ImageNet 的 mean/std 标准化。** 上游推理入口的输入处理与其 normalized VGG 权重配套。M6 用来计算损失的普通 torchvision VGG 是另一条评价路径，应自行执行该评价网络要求的标准化。[S3][S4]

UI 同时说明：实际参与生成与比较的是处理后的内容图。页面可以额外显示原图，但不能把两者混作完全相同的输入。

### 6.3 模型加载

`AdaINEngine` 的初始化应当：

- 先检查权重文件是否存在，与清单指纹是否一致。
- 构造与权重匹配的生成器网络；完整编码器权重应在正确的完整结构上加载，再截取所需输出层。
- 对所选 PyTorch 移植，编码到 relu4_1；不要误用普通分类 VGG、随机初始化解码器或错误截断位置。[S3][S4]
- 按实际 state_dict 结构严格加载；不使用 `strict=False` 把大批未匹配参数静默跳过。
- 优先采用 `torch.load(..., map_location="cpu", weights_only=True)` 读取可信来源的权重字典，处理确实存在的包装层后再加载；不要在不理解报错时直接改成任意反序列化。[S12]
- 将模型移到实际设备，设置 `eval()` 并冻结参数，在生成路径使用无梯度上下文。
- 单个进程/应用实例复用同一套模型，不对每个候选重新加载权重。

最低启动日志：模型路径、SHA256、上游版本、实际 Python/PyTorch/torchvision 版本、设备名称、精度、内容与风格预处理配置。

### 6.4 两个层次的接口

**方便调试的全局接口：**

```python
def stylize_global(content_image, style_image, alpha=0.6):
    """读取或接收图片，生成一个全局强度结果，并返回运行元数据。"""
    ...
```

**供搜索反复调用的接口：**

```python
pair = engine.prepare(content_image, style_image)
result = engine.render_global(pair, alpha=0.6)
```

以上是接口示意，省略号需要真实实现。搜索阶段不能反复使用前一个“从读文件开始”的便捷接口，而应反复调用已准备好的 `pair`。

### 6.5 `prepare` 应缓存什么

对同一个图对计算一次：

- 处理后的内容张量与供 M5 使用的 RGB 图。
- 内容编码特征 `content_features`。
- 风格统计或风格编码所需结果。
- 完整 AdaIN 特征 `adain_features`。
- 内容/风格指纹、权重指纹、预处理配置、设备、精度、实际特征尺寸。

实现 AdaIN 时，按通道在空间维度计算均值和标准差，再进行统计匹配。对同一图对，空间融合所需的两份特征都固定，后续只改变融合比例。

若对齐所选移植，均方差修正方式、epsilon 放置位置都应与其 `calc_mean_std` 一致。该移植使用加 epsilon 后开方的方差；不要在未记录的情况下更换成另一种标准差定义。[S13]

缓存键至少包含图片内容指纹、模型权重指纹、预处理配置和实际设备/精度。仅用文件名作键会在用户替换同名图片后拿到旧结果。

将 `pair` 视为只读。融合时创建新张量，不原地修改内容特征或 AdaIN 特征，否则后一候选可能受到前一候选污染。

### 6.6 生成图的统一口径

解码器输出可能超出显示用 RGB 范围。建议统一产生一个裁到 `[0,1]` 的 FP32 张量，作为 M6 评分、页面预览和 PNG 导出的共同图像来源；原始未裁张量只作可选调试信息。[S4]

搜索评分不要先保存 JPEG 再读回；压缩、量化与磁盘读写都会引入额外变化。评分输入保留张量，转 CPU/PIL 放在展示或导出边界。

### 6.7 先做这三个全局检查

1. 强度为 0、0.6、1 时，输出均完整、有限值、尺寸正确。
2. 强度为 0 时，结果应等于“内容特征经同一解码器重建”的结果，**不要求与原图像素完全相同**。
3. 同一输入与配置重复生成，不应因为遗留状态或随机增强产生变化；跨设备的浮点差异按记录的容差判断，不要求所有设备逐位相同。

## 7 模块三 区域强度与特征融合

### 7.1 你真正要新增的计算

全局强度只有一个数；区域强度则是 N 个数。M5 给你 N 张软掩码，M6 给你 N 个强度，你负责组合出一张空间强度图。

可以分成两步理解：

```text
空间强度图 = 所有区域的“区域强度 × 对应软掩码”逐位置求和

融合特征 = 空间强度图 × AdaIN特征
         + (1 - 空间强度图) × 内容特征
```

随后把融合特征送入同一个解码器，得到整图。

**这一步发生在特征空间，不是在最终 RGB 图上把原图和风格图混合，也不是把不同区域分别裁出来生成再拼接。**

### 7.2 掩码由 M5 做，你负责验证

M5 负责从区域标签生成、缩放和平滑掩码。你要一次性校验：

- `soft_masks.shape == (N, Hf, Wf)`，与实际特征尺寸匹配。
- 软掩码为有限、非负浮点数；不能出现 NaN、Inf 或空覆盖。
- 每个特征位置上，对区域维求和约等于 1；例如初期可采用 `atol=1e-5` 的检查，再按实际数值稳定性统一冻结。
- 区域 ID 的顺序与强度数组一一对应。
- 掩码、特征、强度在相同设备和同一精度下运算。
- 每个待搜索区域在特征层中有有效权重；消失区域交回 M5 合并或处理。

**不要默默把错误掩码归一化后继续。** 归一化本身属于双方约定的构造步骤；如果输入不满足已约定合同，应报告哪个图对、哪些位置或区域有问题。经过明确设计的归一化步骤也应有零分母检查。

### 7.3 核心融合实现示意

下面的辅助函数展示新增计算，可作为你实现时的起点。其前提是上一节的完整验证已经在准备阶段执行。

```python
import torch


def fuse_region_features(
    content_features: torch.Tensor,
    adain_features: torch.Tensor,
    soft_masks: torch.Tensor,
    region_alphas: torch.Tensor,
) -> tuple[torch.Tensor, torch.Tensor]:
    """融合已验证输入；返回新特征和 [1,1,Hf,Wf] 强度图。

    特征形状为 [1,C,Hf,Wf]，掩码为 [N,Hf,Wf]，强度为 [N]。
    调用方保证设备、精度、区域顺序和掩码归一化一致。
    不修改任何输入张量。
    """
    feature_alpha_map = torch.einsum(
        "n,nhw->hw", region_alphas, soft_masks
    )[None, None, :, :]
    mixed_features = (
        feature_alpha_map * adain_features
        + (1.0 - feature_alpha_map) * content_features
    )
    return mixed_features, feature_alpha_map
```

这个函数只负责融合，不加载模型、不读取文件、不调用界面，也不决定强度值。实际公开接口还需检查强度长度、有限性与允许范围。

主实验允许的区域值是 `0.3/0.6/0.9`；融合辅助函数可接受 `[0,1]` 连续值，便于做端点与一致性验证。M6 的搜索入口负责限制正式搜索域。

### 7.4 最重要的正确性检查

**当所有区域的强度都为 0.6 时，无论区域怎样划分，区域融合结果都应与全局 0.6 结果一致。**

原因是软掩码逐位置和为一，组合出的强度图应当处处为 0.6。先检查强度图，再检查融合特征，最后检查同一解码器的输出。初期可在同设备、同精度下用 `rtol=1e-5`、`atol=1e-6` 起步，若需调整应记录原因与最大误差，而不是把容差不断放宽到通过。

这个检查比“目测两张图片差不多”更能证明你确实实现了所声明的公式。

还要做：N=1、某个区域单独变化、区域顺序同步置换、错误长度、未覆盖位置、负权重、非法强度和缓存未被原地修改的检查。

如果某次改动看不出效果，先检查对应掩码是否在特征层还有覆盖。即使有覆盖，解码器也可能让效果扩散到邻区；不能承诺改变区域 A 就只影响原图 A 的像素。

## 8 给 M5 和 M6 的接口

### 8.1 建议放进 `contracts.py` 的数据结构

下面是规格示意，不是完整可运行实现。字段可根据已有项目调整，但调整后应三人同步。

```python
from dataclasses import dataclass
from typing import Any

import numpy as np
import torch
from PIL import Image


@dataclass(frozen=True)
class PreparedPair:
    pair_id: str
    content_rgb: Image.Image
    content_tensor: torch.Tensor
    content_features: torch.Tensor
    adain_features: torch.Tensor
    feature_hw: tuple[int, int]
    input_hw: tuple[int, int]
    cache_key: str
    metadata: dict[str, Any]


@dataclass(frozen=True)
class RegionPack:
    region_ids: tuple[int, ...]
    labels: np.ndarray
    soft_masks: torch.Tensor
    edges: tuple[tuple[int, int, float], ...]
    metadata: dict[str, Any]


@dataclass(frozen=True)
class GenerationResult:
    image_rgb: torch.Tensor
    alpha_map: torch.Tensor
    metadata: dict[str, Any]
```

`frozen=True` 只能限制字段重新赋值，不能阻止张量、字典和 PIL 对象被内部修改。代码仍必须遵守只读约定；必要时在边界复制。

`edges` 的区域编号与 `region_ids` 对齐。M5 提供完整图，M4 的融合只需要掩码与对应强度，M6 使用区域图的关系权重。

### 8.2 你应提供的模型接口

```python
class AdaINEngine:
    def prepare(self, content_image, style_image) -> PreparedPair:
        """预处理并编码一次，返回同图对的只读缓存。"""
        ...

    def render_global(
        self, pair: PreparedPair, alpha: float
    ) -> GenerationResult:
        """生成全局强度结果；不重复编码。"""
        ...

    def render_regions(
        self,
        pair: PreparedPair,
        regions: RegionPack,
        region_alphas: tuple[float, ...],
    ) -> GenerationResult:
        """按固定区域顺序生成结果；不修改缓存，不决定下一状态。"""
        ...
```

对 `RegionPack` 的耗时校验可以单独提供准备步骤，在同一图对上执行一次。不要为了每个候选再次校验整张掩码而引入大量同步或复制。

### 8.3 集成调用应是什么样

```python
# 伪代码：区域函数和搜索函数分别由 M5、M6 提供。
pair = engine.prepare(content_image, style_image)
regions = build_regions(
    pair.content_rgb,
    feature_hw=pair.feature_hw,
    device=pair.content_features.device,
)

default_result = engine.render_global(pair, alpha=0.6)

def generate(region_alphas):
    return engine.render_regions(pair, regions, region_alphas)

search_result = solve(
    generate=generate,
    pair=pair,
    regions=regions,
    initial_result=default_result,
    search_config=search_config,
)

best_image = search_result.best_image_rgb
```

M6 的返回对象至少包含最佳图、对应强度、Q/T/S/J、状态、轨迹、候选数与缓存统计。你不在应用里重新计算另一份目标或自己选一次“最好看的候选”。

### 8.4 必须先和组员确认的六件事

1. M5 输入的就是 M4 预处理后的内容图；双方使用相同的高宽顺序。
2. 区域 ID、掩码顺序、强度顺序固定，并进入缓存身份信息。
3. M6 评分使用你返回的同一张规范图像张量，不自行做另一种裁剪、滤镜或 JPEG 转换。
4. 初始全局 0.6 的结果如何交给 M6，避免默认图在模型层重复生成；M6 的候选预算仍把默认状态计入一次。
5. 模型/特征缓存由你管理；已评价状态的结果缓存和搜索预算由 M6 管理。不同方法的状态缓存独立，不让后运行的方法复用前一方法的候选结果。
6. 错误、取消、预算耗尽和未找到改善的状态怎样返回；“返回默认图”必须标记真实原因。

### 8.5 不等待其他模块完成也能推进

- M5 未完成时，写一个**仅用于测试**的 N=1 或左右两区掩码，验证融合与接口。
- M6 未完成时，手工传入全 0.6 和一组不同强度，验证生成接口；页面显示“接口调试”，不显示为搜索改进。
- 测试替身放在 `tests/fixtures` 或明显的调试入口，不能在正式演示中用它们伪装完整方法。

## 9 模块四 明信片排版和导出

### 9.1 做一个纯函数

建议接口：

```python
def render_postcard(
    image_rgb,
    title: str,
    message: str,
    template: str,
    font_path,

    """生成完整 PNG 字节；函数内不做模型推理或搜索。"""
```

输入可以先统一转换为 PIL RGB 图片，再完成以下工作：

- 用 Pillow 建立画布，采用留白或边框两套简单版式。

字体路径来自配置，不写死你电脑的 Windows 字体目录。提供合法可分发字体，或在 README 中明确获取方式和许可。没有中文字体时给清晰提示，不用乱码、方框或仅适合英文的默认字体冒充成功。

### 9.3 导出验收

- 生成的字节能由 PIL 重新打开，格式确认为 PNG，尺寸和颜色模式正确。
- 中文标题和正文可读，长文本不越界。
- 预览与下载文件一致；重复下载不会触发新的模型推理。
- 两种模板都能运行；空白文本和边界文本都有明确行为。

### 10.2 Streamlit 中最容易写错的地方

- Streamlit 交互会重新执行脚本；模型应通过适合资源对象的缓存方式复用，例如 `st.cache_resource`，而不是每次更改正文都加载一次模型。[S14]
- 图对特征与生成结果放在当前会话状态中；上传内容变化后使旧结果失效。
- 用图片字节指纹、生成配置、模型指纹和搜索配置标识一次图像运行。标题/正文变化只重新排版，不重新跑搜索。
- 先缓存模型，再缓存图对特征，再保存求解结果。这三种状态不能只用一个模糊的 `cache` 字典混在一起。
- 返回结果保留在 `st.session_state`，避免点击下载或修改模板后结果消失。
- 下载按钮使用明确的 `image/png` 类型和预先生成的 PNG 字节。不要在下载回调里再次推理。[S15]
- 运行中展示真实阶段或已评价次数；进度来自实际回调，不假装有精确百分比。
- 初期按本地单用户原型实现。资源缓存可能跨会话共享，模型对象与当前用户图对状态应分开，不对多用户并发能力作承诺。[S14]

### 10.3 接口错误怎样呈现

| 情况 | 正确行为 |
|---|---|
| 权重缺失或不匹配 | 告知缺少的文件、配置位置和真实错误；不产生随机权重结果 |
| 文件名是PNG但实际无法解码 | 停止该次处理，提示重新上传有效图片 |
| 区域掩码和特征尺寸不一致 | 告知接口不匹配，保留诊断记录交M5；不随便裁切掩码掩盖问题 |
| M6搜索失败 | 可保留已经生成的默认图供用户使用，明确标记搜索失败；该运行不能算完整搜索成功 |
| 搜索正常但没有更好可行解 | 显示真实默认回退状态，不称为“搜索显著提升” |
| 无中文字体 | 提示配置字体，禁用不完整的中文导出或明确给出错误 |
| GPU内存不足 | 记录失败和实际设备；不能静默改变正式测试尺寸后继续和其他方法比较 |

## 11 模块六 性能测量

### 11.1 你测什么，M6测什么

你负责生成与应用的性能证据，并提供完整流程的计时外壳。M6 负责搜索算法自身的候选次数、缓存命中、Q/T/S/J 等记录。完整计时应调用真实 M5/M6 模块；结果解释由各自负责成员提供。

| 阶段 | 计时范围 | 是否包含在单次候选生成中 |
|---|---|---|
| 冷启动 | 首次模型构造、权重读取与设备初始化，边界明确 | 单独报告 |
| 图片准备 | 解码、方向、颜色、尺寸与张量转换 | 单独报告 |
| 特征准备 | 内容/风格编码、AdaIN特征、缓存建立 | 单独报告 |
| 单候选生成 | 强度图、特征融合、解码、统一裁剪范围 | 是 |
| 候选评分 | M6评价网络及损失计算 | 不是纯生成耗时，单独报告 |
| 完整搜索 | 区域、准备、求解等实际包含的阶段逐项声明 | 端到端报告 |
| 明信片导出 | 字体、排版、PNG序列化 | 单独报告 |

### 11.2 测量规则

1. 同一设备、图对、尺寸、精度、权重和软件版本。
2. 预热，例如先运行三次；正式至少五次。次数是实验设置，不是已经完成的测量。
3. 使用高精度单调时钟，例如 `time.perf_counter()`。
4. CUDA 异步执行时，墙钟计时前后同步当前设备，或者使用正确同步的 CUDA events；不把任务提交时间当成完成时间。[S16]
5. 记录每次原始耗时，汇总中位数及分布范围。第一次冷启动不混入稳态均值。
6. 测显存前明确重置峰值统计边界，同时记录基线和峰值；`max_memory_allocated` 与保留显存不是同一量。[S17]
7. CPU 模式中 GPU 字段写 `null`，不是伪造为零显存GPU结果。
8. 进程内存可用 `psutil` 采样 RSS；若只取前后值就写前后值，不称精确峰值。若采样峰值，记录采样间隔和“采样近似”的性质。
9. 正式比较各搜索方法时使用独立状态缓存；不要第二个方法免费使用第一个方法已经生成的图片。
10. 性能调试关闭每候选落盘和大图页面刷新；若端到端包含这些操作，须另报对应范围，不能混为同一个指标。

### 11.3 可以做一个有意义的缓存对照

对同一组预先固定的强度状态，比较：

- **未复用编码**：同一图对的每个状态都重新编码内容与风格，再融合、解码。
- **复用编码**：同图对准备一次特征，之后每个状态只融合和解码。

两条路径使用相同图像、模型、数值计算与输出处理，先检查结果一致，再比较时间。两条路径都保留模型加载后的同一模型实例，不把“每次重新加载权重”的劣质实现当作唯一对照。

分别报告特征准备成本、每候选成本，以及 K 个候选的总成本。缓存会占用内存，因此时间改善和内存变化一起记录。只有完成测量后才计算加速倍数。

### 11.4 建议的逐次日志字段

```text
run_id、pair_id、phase、repeat_index、method、seed
actual_device、device_name、dtype、input_hw、style_hw、feature_hw
region_count、model_hash、config_hash、software_versions
elapsed_ms、rss_before_bytes、rss_after_bytes、rss_sample_peak_bytes
cuda_allocated_before_bytes、cuda_peak_allocated_bytes
state_evaluations、decoder_calls、state_cache_hits
status、error_type、error_message
```

不是每阶段都有所有字段；不适用项用 `null`，失败项写失败，不用默认零填满后当作真实测量。

## 16 常见问题定位

| 现象 | 优先检查 |
|---|---|
| 图片颜色异常或完全不成像 | 是否误加ImageNet标准化；权重与网络是否匹配；RGB/BGR与取值范围；解码器是否加载成功 |
| 输出尺寸与输入不一致 | 是否使用约定的固定内容尺寸；实际编码/解码尺寸；是否未经记录处理奇数边长 |
| 全局结果正常，区域结果异常 | 掩码维度、区域ID与强度顺序、逐位置归一化、设备精度、是否误在RGB空间融合 |
| 全部区域0.6却不等于全局0.6 | 先检查强度图是不是常数，再比较融合特征；排查不同预处理或额外滤镜 |
| 前一候选影响后一候选 | 内容/AdaIN特征是否被原地修改；状态结果是否引用可变张量 |
| 换了风格但结果没变 | 缓存键是否只有文件名；是否重新准备同图对；UI是否继续显示旧会话结果 |
| 修改明信片文字特别慢 | 是否错误地重新加载模型、编码或调用搜索；图像与排版状态是否分开 |
| 结果边缘有突变 | 先看软掩码和强度图；再检查特征层区域覆盖与解码器影响，和M5共同定位 |
| 计时非常短但页面明显很慢 | GPU未同步、只计提交时间、遗漏模型加载/评分/转CPU/PNG等阶段 |
| 内存随搜索轮数持续增加 | 是否保留全部中间张量、计算图或重复模型；M6状态缓存是否无限增长 |
| 图片能下载但中文是方框 | 字体不支持中文、路径不存在、用了默认字体或文本布局错误 |
